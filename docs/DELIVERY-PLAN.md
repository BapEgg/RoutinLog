# 루틴로그 구현·검증 순서

대상은 **Android Kotlin·Jetpack Compose 앱 + Kotlin Spring Boot API + PostgreSQL**이다. Android 전용·온라인 전용으로 시작한다. 이 문서는 단계별 계획이며, 프로젝트 뼈대나 샘플 화면이 만들어졌다는 이유로 아래 기능을 구현 완료로 표시하지 않는다.

기존 HTML의 화면 구조·문구·디자인·검증 가능한 계산 규칙을 참고한다. HTML을 그대로 배포하거나 가상 기록을 실제 데이터로 옮기지 않는다. iOS·오프라인 동기화·소셜·랭킹·3D 운동 제작은 이번 단계에서 제외한다.

## 1. 첫 구현 전에 정할 구조

전체 구조도를 먼저 제시하고 앱→인증→서버→DB·외부 서비스 경계를 공유한다. 이후 아래 순서대로 작고 검증 가능한 기능을 연결한다. 서버는 우선 한 개의 배포 가능한 애플리케이션 안에서 계정·계획·기록·식품·리포트 영역을 나눈다. 초기부터 마이크로서비스를 만들지 않는다.

- 앱: Compose 화면, 화면 상태·입력 검증, 서버 호출, 보안 저장소의 세션 정보, 권한 안내.
- 서버: 인증·소유권 검사, 도메인 규칙, 계산·집계, 트랜잭션, 작업 재시도·삭제 처리.
- DB: 사용자별 원본·버전·실제 기록, 중복 저장 방지 키, 리포트·제안 이력.
- 파일 저장소: 실제 사진 기능을 도입할 때 사용자 소유 파일을 DB와 연결. 삭제 대상 추적.
- 외부 연결: Google 인증, Android 건강 데이터, 식품 DB, 이후 OCR·AI. 비밀 키는 앱에 넣지 않는다.

선정한 라이브러리·SDK 버전, 빌드 도구와 필수 환경변수는 실제 빌드 가능한 조합을 확인해서 저장소 안내에 명시한다. 아직 없는 외부 자격증명은 샘플 값으로 성공 처리하지 않는다.

## 2. 단계별 완료 기준

| 단계 | 구현 범위 | 다음 단계로 넘어갈 확인 기준 |
|---|---|---|
| 0. 구조·뼈대 | 저장소 구조, Android·서버 기본 프로젝트, 로컬 PostgreSQL, DB 마이그레이션, 환경설정 예시, 최소 자동 빌드 | 새 환경에서 설명대로 서버·DB와 앱을 실행할 수 있고 앱이 서버 상태를 확인한다. 이 단계는 MVP 완성이 아니다. |
| 1. 계정·프로필 | Google 로그인, 내부 사용자 ID, 서버 인증·소유권 검사, 세션 종료, 온보딩·단위·프로필 버전 | 서로 다른 두 계정이 각자 데이터만 보며, 앱 재시작 후 로그인 상태와 프로필을 안전하게 복구한다. 탈퇴 요청 시 접근 차단을 검증한다. |
| 2. 하루 기록 | 체중·허리·컨디션, 실제 날짜·시간대, 수정 버전, 저장 중/실패/재시도, 중복 저장 방지 | 기록 후 앱을 종료해도 서버에서 복원되고, 같은 저장을 재시도해도 한 건이다. 응답 유실·동시 수정·다른 날짜 수정이 검증된다. |
| 3. 식단 | 유동적인 끼니, 저장 식사, 식품 검색·직접 등록, 원본 기준량과 실제 g 계산, 당시 식품 스냅샷 | 기본 식사를 불러와 달라진 양만 수정할 수 있다. 80g당 160kcal→120g 섭취 240kcal, null 영양값, 조리 전/후와 미래 식단 변경이 검증된다. |
| 4. 운동 | 주간 루틴·프로그램 버전, 날짜별 계획, 종목·세트별 실제 중량·반복, 대체·일정 이동·메모, 휴식 타이머 | 계획 100kg×10회와 실제 80kg×8회를 구분해 재조회한다. 오늘만 변경이 기본 계획이나 과거 기록을 바꾸지 않는다. |
| 5. 활동·주간 리포트 | 건강 권한·걸음 집계, 유산소 입력·추정, 실제 주간 목표/기록 비교, 기록 완전성, 리포트 버전 | 휴대폰·워치 중복과 권한 거절·철회를 처리한다. 일부 영양정보를 한 주 전체 미달로 표시하지 않는다. 과거 수정 후 집계가 갱신된다. |
| 6. 운영·출시 준비 | 전체 계정 삭제 작업, 파일 정리, 데이터 내보내기, 보안·백업·장애 확인, 개인정보 안내, 내부 테스트 배포 | 아래 첫 출시 점검을 통과하고 실제 Android 기기에서 기록→종료→복원→리포트가 동작한다. Play 심사·테스트 요건은 제출 시점 공식 기준으로 재확인한다. |
| 7. 근거 기반 제안 | 검토된 근거·프로그램 저장소, 충분성 판단, 변경 후보·설명, 사용자 적용/수정/보류, AI 실패 시 대체 흐름 | 계산은 코드 결과와 일치하고 임의 출처·칼로리 보상 부채·자동 적용을 만들지 않는다. 제안과 사용자 결정이 버전으로 추적된다. |
| 8. 입력 편의 확장 | 영양표 OCR, URL 분석, 제품 사진, 고도화된 검색·개인화 | 추출값 확인 전 저장하지 않으며 오류·접근 실패·미상 영양값을 처리한다. 기존 수동 기록 흐름은 계속 사용 가능하다. |

현재 목표 범위에는 **실제로 저장되는 기록, 실제 주간 리포트, 검토된 근거를 연결한 수정 제안**이 포함된다. 먼저 수치 리포트까지 연결한 뒤 7단계의 제안과 사용자 적용·수정·보류 흐름을 구현한다. 6단계의 운영 점검은 개발 중에도 진행하고 7단계 완성 후 다시 확인한다. 제안 기능이 미완성인 상태에서는 자동 개인화가 제공되는 것처럼 소개하지 않는다.

각 단계는 UI 전체를 한 번에 옮기기보다 ‘입력→API→DB→재조회’가 끝나는 흐름부터 완성한다. 예를 들어 2단계에서는 체중 기록 한 건을 끝까지 연결한 뒤 허리·컨디션을 같은 규칙으로 확장한다.

## 3. 기록 앱에서 먼저 검증할 것

| 검증 | 구체적인 시나리오 |
|---|---|
| 데이터 보존 | 앱 재시작·로그아웃 후 재로그인해도 기록을 복원한다. A 계정에서 B 계정의 기록이 보이지 않는다. |
| 온라인 저장 | 통신 끊김을 저장 성공으로 표시하지 않는다. 응답을 놓친 동일 요청은 중복 생성 없이 확인·재시도한다. 오프라인 저장 완료나 나중에 자동 동기화한다고 안내하지 않는다. |
| 계획·실제 구분 | 다음 주 루틴을 바꿔도 이번 주 수행값과 당시 목표는 유지된다. 계획 확정만으로 운동·식사 완료가 생기지 않는다. |
| 영양 계산 | 기준량·섭취량·단위와 영양별 null을 검증한다. 제품 정보를 바꿔도 과거 섭취 결과는 당시 스냅샷을 유지한다. |
| 날짜 | 월~일 경계, 자정, 시간대 변경, 과거 수정, 복수 끼니·운동 세션을 확인한다. 하드코딩한 샘플 날짜를 사용하지 않는다. |
| 건강 데이터 | 같은 날 누적 걸음 재조회가 값을 덧셈하지 않는다. 0걸음과 데이터 없음·권한 없음이 다르다. 걸음과 운동 열량을 중복 가산하지 않는다. |
| 리포트 | 일별 당시 목표를 더한다. 불완전한 기록을 0으로 채우거나 변화 원인을 확정하지 않는다. |
| 탈퇴 | 요청 즉시 기존 토큰을 차단하고 비동기 삭제 재시도 후 DB·이미지·파생 리포트·제안까지 확인한다. |
| 접근성·기기 | 실제 기기 글자 확대, TalkBack, 시스템 뒤로가기, 키보드, 화면 회전 정책, 권한 거절, 백그라운드 복귀를 확인한다. |

검증은 중요한 계산·소유권·중복 저장 규칙에 대한 자동 테스트, DB 통합 테스트, 주요 사용자 흐름의 기기 테스트를 중심으로 한다. 단순한 시각적 수정마다 구현을 그대로 반복하는 테스트는 만들지 않는다.

## 4. 배포 전에 필요한 외부 준비

- Google 로그인용 앱·서버 설정과 실제 서명 인증서, 개발/운영 환경의 분리.
- Google Play 개발자 계정·앱 식별자·서명·테스트 트랙, 스토어 설명과 지원 연락처.
- 실제 수집 데이터와 일치하는 개인정보 처리방침, 계정·기록 삭제 경로, 건강 데이터 권한 설명과 신고.
- 식품 DB 사용 범위·출처·갱신 방식, 운동 프로그램·이미지·폰트의 사용 조건.
- 운영 DB와 API 배포, HTTPS, 비밀 키 관리, 백업 및 복원 확인, 오류 감지, 삭제 작업 모니터링.
- 초기 영양 목표와 유산소 추정의 적용 범위·계산 정책 검토. 논문에 있는 공식과 앱이 선택한 정책을 구분.

앱 등록·과금 계정 생성·유료 인프라 사용·운영 배포는 실제 계정과 비용 조건이 정해진 뒤 진행한다. 구조 설계와 로컬 구현은 이 외부 준비와 분리해서 진행할 수 있다.

## 5. 구현 현황을 표시하는 방법

기능 상태는 `설계됨 → 뼈대 작성 → 실제 연동 → 검증됨`으로 구분한다. 화면이 있거나 성공 응답 예제가 있다는 이유만으로 실제 연동·검증됨으로 올리지 않는다.

예: `체중 기록: 뼈대 작성`은 API와 화면 형태가 준비된 상태다. 실제 DB에 저장되고 재로그인·재조회·중복 재전송 검증이 통과해야 `검증됨`으로 표시한다. Google 자격증명이나 실기기가 없어 확인하지 못한 항목은 무엇이 미검증인지 그대로 남긴다.
