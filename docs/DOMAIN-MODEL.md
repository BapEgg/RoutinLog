# 루틴로그 도메인 설계

이 문서는 Android 앱과 Kotlin Spring Boot 서버의 **구현 기준안**이다. 표에 있는 모델·연동·계산이 이미 구현되었다는 뜻은 아니다. 기존 HTML 시안은 화면과 흐름의 참고 자료이며 실제 데이터 저장소로 사용하지 않는다.

범위는 Android 전용, 온라인 전용이다. iOS, 오프라인 저장·동기화, 소셜·랭킹은 이번 범위에 포함하지 않는다. 서버의 기록을 기준으로 화면을 표시하고, 통신이 실패하면 저장 성공으로 표시하지 않는다.

## 1. 변하지 않아야 하는 규칙

1. 계정, 계획, 실제 기록, 분석, 제안은 각각 구분한다.
2. 계획을 적용하거나 체크 화면을 열었다고 실제 식사·운동 기록을 만들지 않는다.
3. 계획·식품·계산 정책 변경으로 과거 기록이 조용히 바뀌지 않게 버전과 당시 값을 보존한다.
4. 미기록, 먹지 않음, 일부 기록, 영양정보 없음은 서로 다르다. 빈 영양값을 0으로 채우지 않는다.
5. AI는 검토된 규칙과 기록을 바탕으로 변경안을 설명한다. 사용자의 확정 전에는 계획을 바꾸지 않는다.
6. 걸음·운동 소비량을 활동계수 기반 목표 열량에 자동으로 더하지 않는다.

## 2. 계정과 사용자

| 모델 | 주요 값 | 역할 |
|---|---|---|
| `User` | `id`, 상태, 시간대, 표시 단위, 생성일 | 서비스 내부의 사용자 식별자. 모든 개인 기록은 이 ID에 연결한다. |
| `ExternalIdentity` | `userId`, 제공자, 발급자, `subject` | Google 로그인 정보. 발급자·subject 조합은 유일하며 이메일은 계정 식별키로 쓰지 않는다. |
| `UserProfileVersion` | 나이 계산용 정보, 성별 입력, 키, 목적, 활동 패턴, 운동 경험·가능 요일, 적용일 | 온보딩·설정의 변경 이력. 분석에는 당시 적용된 버전을 연결한다. |
| `Session` | `userId`, 만료·폐기 상태, 갱신 토큰 해시 | 앱 세션의 갱신·종료·탈퇴 시 접근 차단. Google 토큰을 기록 조회용 앱 토큰으로 그대로 쓰지 않는다. |

Google 인증은 서버가 발급자·대상 앱·서명·만료 등을 검증하고 내부 사용자와 연결한다. 이메일이 같다는 이유만으로 다른 계정이나 제공자를 자동 병합하지 않는다. API는 요청 본문의 `userId`를 신뢰하지 않고 인증된 사용자 범위에서 조회·수정한다.

표시 단위는 kg/cm와 lb/ft/in를 지원하되 계산·저장 기준은 kg/cm/g로 통일한다. 원래 입력값과 단위도 보존한다. 날짜는 사용자 현지 날짜, 발생 시각은 UTC 시각, 해석에 사용한 시간대는 별도로 기록한다. 시간대 변경으로 과거 일자를 일괄 이동하지 않는다.

## 3. 목표·계획·실제 기록

```text
프로필 버전 → 영양 목표 버전
                     ↓
루틴·식사 계획 버전 → 날짜별 계획 스냅샷 → 실제 기록 스냅샷
                     ↓                     ↓
                 당시 목표             실제 수행·변경 사유
                     └──── 주간 리포트 ────┘
                                  ↓
                           제안 → 사용자 결정
                                  ↓ 적용·수정 확정
                             새 계획 버전
```

| 모델 | 주요 값 | 보존 기준 |
|---|---|---|
| `NutritionTargetVersion` | 일일 kcal·탄단지·식이섬유 목표, 적용일, 입력 프로필, 출처, 계산 정책 버전 | 직접 입력과 자동 시작값을 구분한다. 하루 목표가 바뀌면 새 버전을 만든다. |
| `RoutinePlanVersion` | 운동 요일·종목·순서·세트·반복 범위·중량, 프로그램 버전 | 기존 계획을 덮어쓰지 않고 새 버전으로 변경한다. |
| `MealPlanVersion` | 사용자가 만든 끼니 이름·순서와 기본 음식·양 | 아침·점심·저녁 3끼를 고정하지 않는다. |
| `DailyPlan` | 사용자·날짜, 당시 목표·계획 버전, 원래 배치 스냅샷 | 원래 계획과 오늘만 바꾼 계획을 구분한다. 이후 기본 루틴 변경과 분리한다. |
| `PlanAdjustment` | 날짜별 계획 ID, 변경 전·후, 오늘만/이후 범위, 사유 | 자리 없음, 시간 부족, 식재료 변경 등 사용자가 남긴 이유를 보존한다. |
| `BodyDailyRecord` | 날짜, 체중 kg, 허리 cm, 입력 단위, 측정 시각·메모, 수정 버전 | 사용자·날짜별 한 기록을 기본으로 하고 수정 이력을 남긴다. 빈 체중과 빈 허리는 각각 미측정이다. |
| `ConditionDailyRecord` | 날짜, 수면, 피로·근육통·스트레스, 부위·메모 | 수면 0시간과 미입력은 다르다. 주관적 상태를 회복률이나 진단으로 바꾸지 않는다. |
| `MealRecord` | 날짜·끼니 인스턴스, 계획 연결, 실제 음식 스냅샷, 기록 상태 | 같은 끼니를 수정하면 같은 기록을 갱신한다. 추가 끼니는 새 인스턴스로 만든다. |
| `WorkoutSession` / `ExerciseRecord` / `SetRecord` | 날짜·세션, 원래 종목·대체 종목, 실제 중량·반복·완료/생략, 체감·메모 | 세트별 실제 값을 보존한다. 계획 종목이 달라지면 대체 연결을 남기며 서로 다른 기구의 kg를 환산하지 않는다. |

실제 기록에는 참조 ID뿐 아니라 기록 당시 식품·운동 이름, 단위, 중요한 계산 입력의 스냅샷도 담는다. 실제 기록 자체를 수정할 때는 새 수정 버전과 수정 시각을 남긴다. 잘못 입력한 과거 기록을 고치는 것은 허용하되 기존 리포트가 어떤 기록 버전을 사용했는지 추적 가능해야 한다.

### 중복 저장과 동시 수정

- 앱은 저장 작업마다 `Idempotency-Key`를 생성한다. 응답이 유실된 동일 작업을 재전송할 때는 같은 키를 사용한다.
- 서버는 사용자·작업·키의 유일성을 검사한다. 같은 키와 같은 요청은 기존 결과를 반환하고, 다른 본문은 충돌로 처리한다. 보관 기간은 API 정책으로 명시한다.
- 신체·컨디션은 사용자+현지 날짜, 끼니는 사용자+끼니 인스턴스, 운동은 세션·종목·세트 ID로 중복을 제한한다.
- 수정 시 `revision`을 확인한다. 다른 화면에서 먼저 수정된 기록을 오래된 요청으로 덮어쓰지 않는다.
- 저장 실패와 결과 미확인을 구분한다. 결과가 불명확하면 같은 키로 확인·재시도하며 두 번째 섭취나 세트를 만들지 않는다.

## 4. 식품과 영양 계산

| 모델 | 주요 값 |
|---|---|
| `Food` / `FoodVersion` | 이름·브랜드, 출처, 출처 항목 ID, 원본 기준량·단위, g 환산 가능 여부, 조리 전/후, 영양값, 검토 상태·버전 |
| `FoodEvidence` | 영양성분표 이미지 또는 원문 URL, 추출 결과, 사용자 확인 시각 |
| `FoodIntakeSnapshot` | 식품 버전, 먹은 g, 원본 기준값, 환산 결과, 계산 버전 |

g 기준 식품은 `섭취 영양값 = 원본 영양값 × 섭취 g ÷ 원본 기준 g`로 계산한다. 예를 들어 80g당 160kcal인 식품을 120g 먹으면 240kcal다. 원본이 1개·1회분·ml 기준이라면 그 기준을 그대로 보존하고, 검증된 g 환산 정보가 있어야 g 계산에 사용한다. ml를 임의로 g와 같다고 처리하지 않는다.

칼로리·탄수화물·단백질·지방·식이섬유 등은 각각 nullable이다. 알려진 0g과 정보가 없는 `null`을 구분한다. 원본 kcal가 없다고 매크로 계산 결과를 원본 값처럼 채워 넣지 않는다. 추정치를 제공하는 정책이 추가된다면 추정 출처와 계산 버전을 별도로 표시한다.

OCR·URL 분석은 `추출 초안 → 사용자 확인 → 식품 버전 저장` 순서다. 실패하면 이유를 알려주고 사진·직접 입력으로 전환한다. 같은 제품의 영양정보가 수정되어도 과거 섭취 스냅샷은 그대로 남는다.

## 5. 걸음과 운동 소비량

`StepDailyAggregate`는 날짜, 집계 걸음, 공급자, 조회 구간·시간대, 수집 시각, 권한·동기화 상태, 집계 정책 버전을 가진다. Android에서는 Health Connect 등 채택한 제공자의 권한·집계 API를 확인한 후 연결한다.

- 하루 집계는 정한 공급자·집계 정책의 결과로 **교체 갱신**한다. 매번 읽은 누적값을 기존 값에 더하지 않는다.
- 휴대폰·워치 등 여러 출처의 같은 활동을 원시 레코드 합산으로 중복 집계하지 않는다. 제공자의 집계 결과와 선택한 출처 정책을 보존한다.
- 지원 안 됨, 권한 없음, 동기화 지연, 실제 0걸음을 구분한다. UI의 숫자 애니메이션은 새로 받은 값 사이의 표현이며 걸음을 생성하지 않는다.
- 온라인 전용이라도 OS의 건강 데이터 수집까지 항상 네트워크가 필요한 것으로 가정하지 않는다. 앱은 통신 가능할 때 서버로 반영하고 마지막 반영 시각을 표시한다.

`CardioRecord`는 종목·실제 시간·체중·속도·경사·구간·체감·피로·메모, 계산 방법, 근거·버전, 활동 칼로리와 휴식분 포함 총 소비를 구분한다. 직접 입력한 기기값과 앱 계산값을 분리한다. 걸음과 운동에서 같은 활동을 읽었다고 소비량을 두 번 더하지 않으며, 현재 MVP에서는 소비량을 식사 목표에 자동 가산하지 않는다.

## 6. 주간 리포트와 제안

`WeeklyReportVersion`은 사용자 현지 시간대의 월요일~일요일을 기준으로 집계한다. 원본 기록 수정·늦은 동기화가 있으면 새 버전을 만들고 기존 제안이 참고했던 리포트 버전을 남긴다.

필수 구성은 당시 일별 목표의 합계, 실제 영양 합계·일평균, 측정 범위와 체중·허리 추세, 계획 대비 운동 수행·교체, 걸음·컨디션, 기록 완전성이다. 기록 상태와 영양정보 완전성은 따로 계산한다. 예를 들어 먹은 사실을 7일 모두 기록해도 단백질 정보가 2일 없으면 7일 단백질 목표 미달률을 확정할 수 없다.

신체 변화는 관찰된 추세로 보여준다. 특정 식사나 운동 변경이 체중 변화의 원인이라고 단정하지 않는다. 자료가 부족하면 확인 가능한 요약과 현재 계획 유지안을 제공한다. 이전 주 부족·초과 칼로리를 다음 주 목표에 그대로 더하거나 빼는 ‘보상 부채’는 만들지 않는다.

| 모델 | 역할 |
|---|---|
| `EvidenceVersion` | 논문·지침 출처, 연구 대상·설계·한계, 검토자·검토일, 적용 범위를 보관한다. |
| `ProgramVersion` | 작성자, 목적·수준·기구·일정 조건, 프로그램 구성, 참고 근거를 보관한다. 원칙의 근거와 프로그램 전체의 직접 검증을 구분한다. |
| `Suggestion` | 입력 리포트·프로필·계획·근거 버전, 제안 내용·범위·이유·대안, 생성 방법·모델·정책 버전을 보관한다. |
| `SuggestionDecision` | 적용/수정/보류, 사용자가 바꾼 값·이유, 확정 시각, 새 계획 버전을 연결한다. |

계산·집계·유효성 검사는 코드가 담당한다. AI에는 필요한 범위의 정규화된 기록과 검토된 근거만 전달한다. 출력은 구조 검증과 규칙 검사를 통과해야 제안으로 표시한다. AI 실패 시 기존 기록과 숫자 리포트는 사용할 수 있어야 한다. 사용자 수정과 보류는 향후 개인화 자료이며, 효과가 검증되었다는 뜻으로 쓰지 않는다.

## 7. 계정 삭제와 데이터 수명

`AccountDeletionJob`은 요청 사용자, 요청·진행 시각, 단계별 처리 상태, 재시도·실패 상태를 관리한다.

1. 본인 확인 후 사용자를 `DELETION_PENDING`으로 바꾸고 앱 세션·갱신 토큰을 폐기한다. 모든 보호 API에서 계정 상태를 확인해 아직 만료되지 않은 토큰도 차단한다.
2. 예약된 리포트·AI 작업과 새 기록 수집을 막는다. 삭제 진행 중 같은 외부 식별자로 새 계정을 조용히 만들지 않는다.
3. 신체·컨디션·식사·운동·걸음·계획·선택 이력과 파생 리포트·추천을 삭제한다.
4. 영양성분표 사진 등 사용자 소유 파일, 썸네일, 캐시·검색 파생 데이터와 외부 처리업체에 보낸 데이터의 삭제 범위를 처리한다. 공공 공용 식품 데이터는 사용자 소유 자료와 구분한다.
5. 삭제 작업은 재시도해도 안전하게 처리하고 상태를 확인할 수 있게 한다. 백업 보존기간·법적 보관 예외·외부 제공자 보존정책은 실제 운영 정책과 사용자 안내에 일치시킨다.

운영 로그에는 식단·신체값·사용자 메모·인증 토큰을 통째로 기록하지 않는다. 백업을 복원할 때도 이미 삭제한 계정이 다시 활성화되지 않도록 삭제 상태를 반영한다.
